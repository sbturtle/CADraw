# 로컬 손글씨 OCR 실험

ADR-0018의 근거입니다. 조건은 무료·상업 사용 가능, VRAM 4GB 이내(또는 CPU),
Windows에서 `uv sync`나 `ollama pull`로 설치 가능한 것이었습니다.

## 재현

```powershell
uv run python scripts/run_ocr_benchmark.py
# 선택: 로컬 비전 모델 교차 판독 (ollama pull qwen3-vl:4b-instruct 필요)
uv run python scripts/run_ocr_benchmark.py --cross-check qwen3-vl:4b-instruct
```

정답지는 `ocr-ground-truth.json`입니다. 원본 사진 7장에서 사람이 의심 없이 읽을
수 있는 손글씨 치수 75개의 값과 글자 상자 중심을 담았습니다. `Ø`, `°`는 값에서
뺐고 `R`은 남겼습니다. 인쇄된 양식 글자와 가격, 수량은 넣지 않았습니다. 각
라벨은 중심을 포함하는 검출 상자의 파싱 값이 같을 때 정답입니다. 검출 재현율이
아니라 인식 정확도를 재는 집합입니다.

## 후보 선정

| 후보 | 라이선스 | 크기/자원 | 판단 |
| --- | --- | --- | --- |
| RapidOCR 3.9.2 + PP-OCRv6 small | Apache-2.0 | 모델 31MB, CPU | **채택 (1차 판독기)** |
| RapidOCR + 한국어 PP-OCRv5 mobile | Apache-2.0 | 13MB, CPU | 숫자 정확도 낮음 |
| Qwen3-VL 2B/4B `-instruct` (Ollama) | Apache-2.0 | 1.9/3.3GB, VRAM 2.0/3.5GB | **선택 (교차 판독)** |
| Qwen2.5-VL 3B | Qwen Research License | 3.2GB | 비상업 전용이라 제외 |
| Gemma 4 E2B | Apache-2.0 | 7.2GB (QAT 4.3GB) | 4GB 초과 |
| PaddleOCR-VL 0.9B | Apache-2.0 | 0.9~1.8GB | Ollama 태그가 커뮤니티 배포뿐이라 보류 |
| Surya | 수정 OpenRAIL-M | torch 필요 | 매출 조건부 무료라 제외 |
| EasyOCR, Florence-2 | Apache/MIT | torch 필요 | 손글씨·한국어 미지원 |

PP-OCRv6은 2026-06에 나왔고 RapidOCR 3.9의 기본값입니다. 한국어는 지원하지
않지만, 이 도면에서 필요한 것은 숫자와 `R`, `°`입니다.

## 인식 정확도 (75개 라벨)

| 판독기 | 정답 | 비고 |
| --- | ---: | --- |
| 이전 기본값 (OCR 꺼짐, Tesseract 미설치) | 0 | `OCR_UNAVAILABLE` |
| PP-OCRv6 small, 검출 사변형 그대로 인식 | 59 (79%) | RapidOCR 기본 파이프라인 |
| PP-OCRv6 small, 여백 12px 크롭 재인식 | 63 (84%) | 탐색 단계 |
| **PP-OCRv6 small, 출시 경로** | **61 (81%)** | 여백 짧은 변 10%(최소 4px), 배치 인식, 파싱 기준 |
| PP-OCRv6 tiny | 47 (63%) | |
| 한국어 PP-OCRv5 mobile | 37 (49%) | 숫자를 `{`, `$`, `이`로 오독 |
| 영어 PP-OCRv4 mobile | 31 (41%) | |
| Qwen3-VL 2B instruct | 56~59 (75~79%) | 프롬프트에 따라 다름 |
| Qwen3-VL 4B instruct | 54~55 (72~73%) | 2B보다 낫지 않음 |
| Qwen3-VL 4B (태그 없음, thinking) | 0 | 생각에 토큰을 다 써서 빈 응답 |
| 다수결 (PP-OCR ×2 + Qwen3-VL 4B) | 64 (85%) | 단일 판독기 대비 +1 |

여백은 결과에 크게 영향을 줍니다. 원본 사진에서 짧은 변의 25% 여백은 56개로
떨어졌고(이웃 획이 들어옴), 10%는 62개, 고정 12~16px는 63~64개였습니다.
저해상도 스캔(`pure_background`, 라벨 위치는 SIFT 호모그래피로 옮김)에서는
여백과 거의 무관하게 49~53개(65~71%)였습니다. 여백보다 해상도가 더 중요합니다.

## 교차 판독의 가치

VLM을 더해도 정답 수는 늘지 않습니다(1차 값을 바꾸지 않으므로 61개 그대로).
대신 두 판독기의 일치 여부가 신뢰도 신호가 됩니다. 아래는 출시 경로
(`run_ocr_benchmark.py --cross-check`) 결과입니다. 라벨 위치에서 파싱된 값은
71개이고 그중 1차 판독 오류는 10개입니다.

| 구분 | 교차 판독 없음 | + Qwen3-VL 2B | + Qwen3-VL 4B |
| --- | ---: | ---: | ---: |
| `검토 필요`로 남은 값 (정답) | 71 (61, 86%) | 52 (48, 92%) | 51 (49, 96%) |
| `불확실`로 낮춘 값 (그중 1차 정답) | 0 | 19 (13) | 20 (12) |
| 1차 오류 중 `불확실`로 잡힌 것 | 0/10 | 6/10 | 8/10 |
| 사진 한 장당 추가 시간 | – | +7~13초 | +8~10초 |
| VRAM | 0 | 2.0GB | 3.5GB |

비교 전에 두 번째 판독의 양 끝에서 지시선과 화살촉 기호(`-200-`, `<159`,
`200x`)를 떼어 냅니다. VLM은 라벨에 닿은 지시선까지 받아 적기 때문입니다.
떼어 내지 않았을 때는 1차 정답인데 `불확실`이 된 값이 15개였습니다(4B·2B 모두).

`불확실`로 낮춘 값의 60~68%는 1차 판독이 맞았습니다. 교차 판독은 오류를
걸러 주는 도구가 아니라 먼저 볼 곳을 좁혀 주는 도구입니다. 경고에는 두 판독을
함께 적으므로(`590 / 510`) 두 번째 판독이 맞은 경우 바로 고를 수 있습니다.
7번의 `510`(PP-OCR은 `590`)과 `160`(PP-OCR은 `60`)이 그런 경우입니다.

가장 위험한 오독도 걸립니다. 손글씨 `790Ø`를 PP-OCR은 그럴듯한 길이 `7909`로
읽고, Qwen3-VL 2B는 `790°`, 4B는 `7969`로 읽습니다. 모두 틀렸지만 서로
다르므로 불확실로 표시됩니다.

4GB 한도 안에서는 4B가 오류를 더 많이 잡습니다. VRAM이 빠듯하거나 속도가
중요하면 2B를 씁니다. 다른 프로그램(예: 게임)이 GPU를 99% 쓰는 동안에는
크롭 하나가 30초 제한을 넘겼습니다. 그러면 판독기는 한 번 실패한 뒤 멈추고
`SECOND_READER_UNAVAILABLE`을 남깁니다. 기본으로 꺼 둔 이유입니다.

## 속도

다른 부하가 없을 때 4000×2252 원본 사진 한 장의 검출과 인식은 평균 1.3초
(CPU, 4스레드)입니다. 전체 분석은 사진당 3.6~8.0초에서 5.0~9.1초로, 1.1~1.9초
늘었습니다. 다른 무거운 프로그램(게임)이 CPU를 쓰는 동안에는 OCR만 평균
4.4초였습니다.

아래 스레드 비교는 그 경합 상태에서 1448×1086 스캔 한 장으로 잰 값입니다.
기본 설정이 경합에서 얼마나 무너지는지를 보여 줍니다.
